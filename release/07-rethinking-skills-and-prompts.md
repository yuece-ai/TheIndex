# 换上 GPT-6 Astra,重新梳理你的 skill 和提示词

> 翻译自 Eric Provencher(@pvncher,OpenAI Codex DX)2026-09-04 发在 X 上的文章《Rethinking skills and prompts for GPT-6 Astra》。这是"前沿从业者怎么说"栏目,面向已经在用编程 agent 的人,术语不做通俗化处理。

![原文配图:左边一团缠在一起的文档,向右收拢成三份清爽的文档。](07-rethinking-skills-and-prompts.jpg)

编程 agent 这一年进步很大,最佳实践也在快速变化。以前需要大量手把手引导和脚手架的地方,现在不需要了。

如果你过去一年一直在项目里用 agent,你多半已经攒了一大堆臃肿的指令——都是当初为了把模型引向好结果一点点加上去的。每次模型更新,都值得回头重新审视这些假设,而换上 GPT-6 Astra 之后,这件事比以往都重要。

这些指令形式很多:Skill、AGENTS.md、你的任务提示词,都在塑造模型怎么干活。

## Skill 文件

其中一种形式是 skill 文件——本质上是存成 markdown 的提示词,有时还捆着脚本。它们最有用的场景,是给模型只在某些任务里才需要的工作流做引导,或者说明怎么用某个插件。

很多人习惯往项目里下载一大堆 skill,这是个错误。每个 skill 都带一个名字和描述,会被加载进模型的 context,好让它知道什么时候该用。很多描述写得太长;而 skill 一多,Codex 就开始压缩这些描述好塞进 context。结果模型看到的每条描述都变少了,更难判断该选哪个。

更糟的是,描述之间可能互相矛盾,或者写得太有"选我选我"的劲儿,把模型引去加载一些对当前任务根本没用的指令。

如果你让 Codex 帮你建过 skill,它多半用的是 `$skill-creator` 这个 skill。我们最近改了它的几条指引,来缓解实践中见到的一些失败模式。

**第一,skill 的描述要尽量短,同时说清楚模型什么时候该用它。**

(原文这里有一张好/坏描述的对比图。)坏的描述会推着模型"只要碰到跟数据库有关的任何东西"就用它,而不是"只在要处理迁移时"才用。

**第二,一个有用的 skill,关键标志之一是渐进式披露(progressive disclosure)。** 读一个 skill 要占 context,让你更快逼近压缩点,还会引入一些可能不适用于当前任务的指引。对于有多个工作流的 skill,把根文档做成一个最小的路由,指向支撑文档和脚本。给模型足够的引导让它知道该去哪儿找,但别逼它读那些此刻无关的东西。

**第三,很多 skill 被写成了事无巨细的行程单或菜谱。** 模型理解细微差别和模糊表达的能力已经强了很多,所以过度具体的引导,在以前有帮助的地方,现在反而碍事。

仓库里的 skill 也会指挥其他贡献者的 agent,而那些 agent 可能用的是别的模型。对 Sol 或 Luna 有帮助的引导,可能把 GPT-6 Astra 框得太死——所以要考虑清楚,你留下的这些指令,会被哪些模型用到。

## AGENTS.md

因为 AGENTS.md 在模型每次进你的仓库干活时都生效,逐条回看每一条指令,问问这个任务是不是还需要它。

要求模型每次编辑前先读一摞文档、或看完整的仓库地图——对一个改错别字的任务来说,这太过了。GPT-6 Astra 能自己判断需要读什么,不用你推着它在每次改动前把整个项目审一遍。

(原文此处有一张图。)

让模型在每次编辑前都读文件,是烧 context、拖慢进度的好办法。但指向一部分文档仍然有用,前提是这个指向要看情况。也记得把你的文档保持更新。

以前的模型需要你鼓励它去跑测试、检查自己的工作。GPT-6 Astra 会自己做,所以同样的指令可能导致不必要的测试。

GPT-6 Astra 做事很周全,但它在"一个任务该做到多深"上会更犹豫。有时候它需要你推一把才继续。你可以用 AGENTS.md 给它开一个你确知安全的工作流的权限,比如一套本地测试:

> 本地测试用的是一次性的 fixture,没有生产环境访问权限。跑它们,修掉本次改动引起的失败,重跑受影响的测试,不用每一步都来问我批准。

## 决策边界

要特别注意你怎么描述边界。如果以前有个模型未经许可就替你做了事,你可能加过一些强硬措辞,逼它先问。这有用,但 GPT-6 Astra 的判断力好得多,你应该照这个来对待它。它也会认真对待你的边界,可能在一些你其实巴不得它继续的地方停下来。

## 该不该停

如果你习惯了 GPT-5.6 Sol 接过一个请求就连续干很长一段,GPT-6 Astra 会让你觉得它在"什么时候停"上更犹豫。它可能做出第一版实现,就回来让你 review,而其实活还没干完。

这时候,开工前先定义"什么算完成"就很有用。如果任务包括把实现跑起来、检查结果、修掉失败的部分,就把这些写进请求里。一句"做完第一版就停下来等我 review",会把模型拉向一个更早的停止点——所以想清楚,这是不是一个你真的需要自己来做的决定。

如果你想让它在第一版之后继续探索,就说清楚你要它探索什么、在哪儿停。

换个新模型,是打扫房子的好机会。让 GPT-6 Astra 照这篇文章讨论的内容做一次审计,然后去做一件你以前不敢试的事。
