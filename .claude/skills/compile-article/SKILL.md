# 编译一篇文章

`AGENTS.md` 是唯一事实源,本 skill 只是把协作步骤排成流程。每一步做完再进下一步,不跳步。

产物放 `release/<slug>/`(或 `release/NN-<slug>.*`,跟现有文件的命名保持一致):
- `<slug>.en.md` — 原文,逐字保留,绝不覆盖
- `<slug>.md` — 通俗编译稿
- `<slug>.<ext>` — 配图
- 需要时 `<slug>.zh-en.md` — 逐段中英对照

---

## 第 0 步:拿到原文

- 链接优先用 `curl -sL -A "Mozilla/5.0 …"` 抓,提取正文段落,存 `<slug>.en.md`(标题、副标题、作者、日期在前)。
- 抓不到就请用户贴正文。
- 通读一遍。不清楚论证前不进下一步。

## 第 1 步:判定是否值得收录

先过硬门槛(任一不过 → 不收,直接告诉用户为什么):

1. **删掉 AI 后文章还完整吗?** 完整 → 不收。
2. **它咬住了一个具体问题吗?** 一句大白话能说清"它在问什么",且普通人会点头"我也想过";如果反应是"有意思,但不是我的事" → 选题或切入口有问题。
3. **里面有人、物、机制或选择吗?** 只有观点、没有具体载体 → 不收。
4. **它是新闻 / 参数复述 / "普通人如何抓住机会"吗?** 是 → 不收。当下索引不追发布。

再过价值门槛:

5. **它能收回到一个问题,然后要么落一个判断,要么抛一个更深的问题吗?** 只是"一个有趣的研究" → 不够。
6. **读者读完,会重新打量自己生活里的什么?** 说不出来 → 还不成熟。
7. **文章本身够好、够自足吗?** 论证靠定义硬撑、或半篇是易腐的预测和跑分 → 只适合当"多来源里的一个",不适合整篇编译,建议用户改走原创稿。
8. **立场会不会和 `release/` 里已有的稿雷同?** 现有稿如果已经几篇都在讲"AI 侵蚀了某种人的能力",再来一篇同调的会把号做成"AI 怀疑号"。提示用户,让他决定是否仍要收,或换一篇补别的栏目/别的立场(经营决策、前沿、有现场、偏正面或混合)。

输出:一句结论(收 / 不收)+ 逐条理由。不收就停在这里。

## 第 2 步:通俗编译(按 AGENTS.md《编译》)

只在拿到授权后 publish(个人 newsletter 一般发邮件可谈;大刊和签约作者风险高)。编译稿可以先做出来,publish 前再确认授权 —— 做完提醒用户。

- **验收标准:一个受过教育的普通读者,每句话第一遍就读懂。一个懂技术的人读着卡壳,就是没做完。**
- 保留论证和作者的语气、第一人称转述("Sacasas 说""他觉得"),不保留原文的句式和抽象度。
- 每一个抽象论断都要落成具体的事或一个日常例子。译到抽象处停下来问:这句话能还原成人、物、机制、数字或决定吗?不能就重写。
- 引文改成转述,只留带画面的那几句(如"引开看门狗的肉""就着盐吸可卡因")。哲学家引哲学家的链条压掉;次要来源压成一两句。
- 删原文的开场客套、邮件通讯说明、写给订户的旁白、文末推荐阅读。
- 术语躲不开时当场用人话解释;能删的术语名字直接删,只留功能描述。
- 原文若是几年前的,内容里有已经过时的经验、预测或跑分:不改原意,用方框"编者注"补一句现在的情况(这也正是当下索引"过几个月回来核对"的做法)。编者注要少而准,一篇最多两三条,并在文首说明"编者注是编译时补的"。
- 作者、原文出处、发表日期放在文首。

## 第 3 步:流畅性检查(装成读者挑毛病)

把自己当成"想了解 AI 的普通人",从头读一遍,专门找:

- **看不懂的句子**:直译腔、宾语缺失、指代不清、一句话绕三层。逐句改。
- **术语漏网**:还有没有没解释的词。
- **入口太远**:每一节是不是从一个具体场景/例子进,而不是从概念进。故事出场前,读者知不知道这节在追问什么、跟他什么关系。
- **译错 / 译反**:关键数字、专有名词、因果方向,回 `<slug>.en.md` 逐个对。
- **假人味**:为显得有人味而抖机灵、加俏皮话、硬凑口语 —— 判废。人味来自判断和具体,不来自语气。

把找到的毛病列出来,逐条改,然后把"挑出的毛病 → 改法"表给用户看。

## 第 4 步:分段标题 + 加黑

- **小标题**:一节一个意思。标题要说清这节在讲什么,不能含糊(反面例子:"太顺手了""老媒介研究者早说过" —— 读者不知道指什么)。也不表演聪明。
- **加黑**:默认不加。加黑 = 宣称这是金句。只有满足才加:
  - 是一句能独立拎出来的判断或转折,不是加黑的解释文;
  - 简洁、有刀口、能吸引人往下读;
  - 全篇加黑不超过 3–4 处,多了就稀释。
- 加完自己数一遍加黑处,逐个问:这是金句吗?不是就取消。

## 第 5 步:配图

每篇一张,存 `release/<slug>.<ext>`。要求:**高级,和文章匹配,来源干净**。

按顺序找:

1. **原文自带的图**:如果原文有一张真正好的主图(作者拍的实验图、艺术作品、有信息量的图表),且授权允许,用它。`curl` 下载,记下出处。
2. **公共领域 / 开放授权的真实图片**:Wikimedia Commons、各大博物馆 open access(Met、Rijksmuseum、Art Institute of Chicago)、Unsplash。挑一张和文章的核心意象对得上的 —— 不是配一张"科技感"通用图,是配一张能让读过文章的人会心的图(例:讲复印机失真就找复印机/JBIG2 失真图;讲"AI 是环境"就找一张把人包裹进去的空间)。
3. 都没有合适的:向用户描述需要什么样的图,让他来定,不硬凑。

配图定稿前:确认是真实存在的图、授权清楚、和正文意象对得上、不是俗套的 AI 插画风。把图的出处和授权写进交付说明。

## 交付

给用户:
- 收录判定结论
- `<slug>.md` 路径
- 第 3 步的"毛病 → 改法"表
- 加黑清单(几处,分别是什么)
- 配图:文件路径 + 出处 + 授权
- 授权提醒:publish 前是否已联系原作者
